# Publishing to the CardputerZero app store

Everything here was read out of the store's own repositories and workflow code on
2026-11-25, not from a summary. Where a policy is enforced, the enforcing line is cited.

## The short version

**The package is ready. The submission is not blocked on code — it is blocked on hardware.**
A first release needs a video of the app running on a real device, and the CardputerZero has
not arrived.

## Two channels, same checks

| | `czdev publish` (CLI) | `dev.cardputer.cc` (web) |
|---|---|---|
| where the `.deb` lands first | a Release in **your own fork** of `CardputerZero/packages` | the official `staging` Release, name-prefixed with your login |
| size limit | 2 GiB per asset | 80 MB by default |
| then | opens a PR touching only `pool/main/` | a trusted workflow opens the PR |
| validation | `validate-pr.yml`, read-only sandbox | the same policy scripts |
| **first release** | **human review + device demo** | **human review + device demo** |
| later updates | auto-merged once checks pass | auto-merged once checks pass |

Both channels share `install_path_policy.py`, so a rejection reads identically either way.

### The first-release gate is in the code, not just the docs

`CardputerZero/packages/.github/workflows/validate-pr.yml:316`

> First release of a new package name is gated on a human: the privileged stage re-derives
> this on its own and will not auto-merge

`validate-pr-comment.yml:99`

> the first release of a new package name stays open until a maintainer has watched the demo
> video and merges by hand

The dev-portal README says automated review merges with no human intervention. That is true
of **updates**. It is not true of a new package name.

## Package-name ownership is first-come-first-served

From the portal README and `validate-pr.yml:55`: ownership is claimed by whoever submits a
package name first, recorded as `uploaded_by` (a GitHub login). Afterwards only that account
or an admin can update or withdraw it. The `.deb`'s `Maintainer` email is *not* matched
against the GitHub account.

So `p4wnp1-panel` is unclaimed until someone submits it.

Reproduce the first one:

```bash
curl -fsSL https://raw.githubusercontent.com/CardputerZero/packages/main/.github/scripts/install_path_policy.py -o /tmp/install_path_policy.py
python3 -I /tmp/install_path_policy.py p4wnp1-panel app/dist/P4wnP1_0.3.1_rev1_arm64.deb /tmp/bad.txt
test -s /tmp/bad.txt && cat /tmp/bad.txt || echo "no rejected paths"
```

## When the hardware arrives

1. Install the `.deb` on the device and confirm it runs — this is also the first arm64 boot
   this codebase has ever had, so expect to find things.
2. Record a short video of the panel running on the device. A phone recording is explicitly
   acceptable.
3. Re-check the claims the README currently marks as unverified: dwc2 device mode, the
   Host/Slave switch, the real endpoint budget, and what gadget mode costs.
4. Submit:

```bash
czdev login
czdev publish --deb app/dist/P4wnP1_0.3.1_rev1_arm64.deb
```

5. Post the video in the PR it opens, and wait for a maintainer.

Only step 2 and the waiting are things the code cannot do for itself.

## Afterwards

Version updates merge on validation alone, so the second release onwards is
`./build-deb.sh && czdev publish`. An app keeps only its highest Debian version in the store;
the publish PR removes older manifests in the same change.
